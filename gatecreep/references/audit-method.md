# 门禁审计方法

## 1. 范围与事实

确认目标路径、审计范围、是否启用过度设计和报告位置。辅助脚本输出字段：

- `capabilities`：入口候选、CLI 命令、Agent 工具及其输入、返回和可达门禁；
- `gates`：条件、动作、限制、异常及源码位置，不含合理性结论；
- `flows`：调用关系，`confirmed` 为静态确认，`inferred` 为未解析或动态路径；
- `documents`：可能的契约来源；
- `coverage`：解析失败、动态注册和未映射门禁等覆盖缺口。

脚本失败时保留错误并报告检查未完成。按需读取源码和文档，不执行目标项目。

任何非零退出的 stdout 都视为无效，包括写出失败后的部分 JSON；保留 stderr 中的失败阶段并列入覆盖缺口。脚本使用目标目录外的临时序列化文件，不静默截断；事实仍驻留内存，大项目需要限定审计范围。

先审阅 `excluded-directory`、`excluded-file` 和 `unreadable-directory` 等范围记录。虚拟环境、缓存及外部链接未纳入扫描，不等于整个仓库已覆盖；非 Python 执行链仍需明确列为审计边界。

按 `source_role` 区分测试候选与来源未知的事实，不用测试断言密度推断产品门禁。测试可以支撑契约、恢复行为或反证；unknown 需要结合项目结构核对。

## 2. 建立公开功能清单

逐项记录：

| 字段 | 要求 |
|---|---|
| 功能 | 公开命令、工具或 Skill 能力，不把内部辅助函数单独算作功能 |
| 声明 | 文档原文、位置和适用范围 |
| 实现 | 文件、函数、命令或注册位置 |
| 输入 | 必填、可选、默认值、类型、取值与边界 |
| 输出 | 成功、失败、部分结果和状态语义 |
| 前置条件与副作用 | 权限、环境、依赖、配置及外部状态变化 |
| 识别状态 | 确认、推断或未知 |

声明没有实现、实现没有声明、动态注册和不可读文件都列入覆盖缺口。不得把“未识别”写成“不存在”。

MCP 的 `declaration_kind: mcp-tool` 证明工具声明存在，不能单独证明注册已生效或实现可达。`mcp_role` 只记录分派、列举角色的语法推断，不作为具名工具；逐工具实现无法确认时保留 `unresolved-tool-implementation`，不得把共享分派器所有门禁分配给每个声明。

建立双向映射：每项功能列出路径上的门禁；每个门禁列出受影响功能。无法映射的门禁单列，不强行分配功能。

## 3. 定义合法任务与成功标准

每项功能先写：

1. 合法输入及正常使用方式；
2. 必要前置条件；
3. 成功输出与副作用；
4. 可接受的部分成功、空结果和降级；
5. 明确非法输入及合理拒绝。

契约不清楚时列入证据不足，不自行创造合法输入。非法输入被按契约拒绝不属于任务失败。

## 4. 生成代表性失败场景

仅分析与正常任务有关的场景：

- 合法输入或合法边界被拒绝；
- 单项或可恢复失败扩大为整批或整个任务失败；
- 达到限制后提前结束，核心结果缺失；
- 部分、失败或空结果被当成完整或成功；
- 公开能力没有可达实现路径；
- 文档声明的输入输出与实现行为冲突。

每个场景必须对应功能、合法任务和成功标准。不要穷举纯理论异常，不扩展到无关代码质量。

## 5. 建立因果链并分类

按以下形式记录：

```text
合法任务与输入
→ 执行路径 [静态事实/模型推断]
→ 触发条件或异常 [源码]
→ 上层处理 [源码]
→ 最终结果及与成功标准的差距
```

动态分派、不可行路径和未读取实现必须标为推断。推断路径不能成为契约冲突的唯一证据。

**失败来源**只选适用项：有意门禁、实现异常、外部环境或前置条件、合理拒绝、证据不足。

**外在表现**另选：明确拒绝、异常终止、静默跳过、截断、部分结果冒充完整、错误成功、无法到达出口。

门禁通过异常实现时，来源仍是门禁，异常是表现。非门禁原因只在其解释任务失败时记录。

## 6. 评估门禁

### 6.1 证据强度

1. E1：机器可读契约、Schema、CLI 声明、结构化安全策略；
2. E2：明确用户要求、README、Skill/Agent 能力声明、设计或安全文档；
3. E3：可验证的权限边界、事务、顺序依赖、平台限制等代码约束；
4. E4：命名、注释和实现习惯，只作线索；
5. E5：模型一般经验，只作解释，不能独立支撑发现。

证据必须适用于当前功能和输入范围。高优先级安全或权限要求不能被“用户想完成”覆盖。

### 6.2 必备分析

- **保护目标**：安全、权限、契约、一致性、资源还是未说明的保守假设；
- **风险范围**：哪个对象、动作和资源实际受影响；
- **处置范围**：确认、单项拒绝、降级、截断、整批终止还是全局禁止；
- **恢复路径**：重试、分批、配置、替代流程、人工确认或没有；
- **可见性**：拒绝、跳过、失败和不完整状态是否被准确传播；
- **反证检查**：哪些安全、权限、事务或平台依据可能使门禁合理。

### 6.3 五档结论

**契约冲突**：明确的 E1/E2 契约与静态确认的实现行为直接矛盾，且没有适用的同级约束。必须双向引用证据。

**疑似过度门禁**：合法任务、门禁动作、影响路径均明确；处置超出可识别风险或限制静默改变结果语义；反证检查后仍无不充分的合理解释。结论保持“疑似”，因为尚未动态验证和人工确认。

**合理门禁**：有适用安全、权限、一致性、平台或公开契约依据。任务想完成但被拒绝，不改变这一分类。

**非门禁问题**：失败主要来自实现异常或外部环境。只记录与任务失败有关的因果链。

**证据不足**：合法任务、路径、保护依据或影响任一关键部分无法确认。文档没有提及某个保护，不等于证明它多余；破坏性操作、认证和授权尤其需要明确依据才能建议调整。

常量值、不可配置、变量名、注释中的“危险”、单个 `raise` 或模型经验均不能单独形成主要发现。

## 7. 可选过度设计

仅用户明确请求时执行。必须指出对正常任务的具体代价，例如重复校验导致规则冲突、可自动传递的数据被要求多次人工转换、非关键步骤阻断主流程、复杂降级隐藏真实失败。

流程长度、层数和代码量本身不是证据。结果放在独立章节，不计入过度门禁发现。
